# Decisions

Log of spec ambiguities and deviations, most recent first.

## 2026-09-16 — M11: Notifications & Settings

- **Added `Features/Settings/ReminderSection.swift`**, not in §5.2's file list (which only names `SettingsView.swift` and `WhatsAppContactSection.swift` under `Settings/`). §10.12 item 1's reminder toggle, Day/Time pickers, permission handling and footer are enough self-contained logic to keep `SettingsView` itself small and under the ~250-line guideline, matching the precedent of `WhatsAppContactSection` already being its own file for item 2.
- **§9.2's "re-sync the reminder" on `scenePhase == .active` is split across two places.** `RootTabView.onBecomeActive()` (alongside the existing `archiveEndedWeeks()`) owns the actual reschedule: if `reminder.enabled` and still authorised, it calls `scheduleWeeklyReminder` again (cheap and idempotent, and it runs even if the user has never opened Settings this launch — mirroring the M9 precedent that a `Tab`'s content is lazy but a view outside it is always live). `ReminderSection` separately refreshes its own `authorizationStatus` on `.task`/`scenePhase == .active` purely to update the footer's denied-permission warning, and does not reschedule from that path — rescheduling there is only triggered by the user's own actions (toggle on, day/time change), so the two don't duplicate each other's writes.
- **The denied-permission footer copy isn't given verbatim** — §11.3 only quotes the alert text ("Notifications are off"). Used "Notifications are turned off for MealPlanner. Turn them on in Settings to get this reminder." for `ReminderSection`'s footer, in the same tone as the alert and the WhatsApp section's own invalid-number caption.
- **`NotificationScheduler.nextReminderDate` and `.footerText`** (pure, `Calendar`-only helpers) added beyond §8.6's given `NotificationScheduling` protocol, same precedent as `LeftoverRules`'s copy-builders (M7) — §11.3's footer ("Next reminder: Sunday 20 Sep at 18:00") needs a testable pure function rather than being computed inline in the view. Covered by `NotificationSchedulerTests`; the protocol's four live `UNUserNotificationCenter`-backed methods aren't unit tested (Simulator permission prompts aren't something a test run can answer).
- **`SettingsView`'s "Add Example Meals" (§10.12 item 3) is a second call site for `MealStore.addSampleMeals()`**, alongside `MealLibraryView`'s existing empty-state button (M2/M4). They're deliberately different: the library's is a silent convenience action on an empty screen, while Settings' shows the exact alert text §10.12 asks for ("Added N example meals.").

## 2026-09-16 — M10: Export & WhatsApp

- **"Send to `<Name>` on WhatsApp" is gated on a non-empty (trimmed) name as well as a `.valid` phone**, not just the phone as §12.2 literally says ("only if the saved phone is `.valid`"). A saved number with no name would otherwise render as "Send to  on WhatsApp" (double space, no name) — requiring both is the simplest fix and matches §14's "Invalid saved WhatsApp number → 'Send to `<Name>`' is hidden" intent that the row always reads sensibly.
- **The share menu (⬆︎) is shown even on an ended (read-only) week**, while `+` (Add Item) and `⋯` (Untick All) stay hidden. §10.10 is explicit that "Sharing is still allowed" for a frozen list, and `WeekPlanService.markShared` (M9) already no-ops safely on an archived week — so the menu only needed to move outside the `!isReadOnly` toolbar block, no service changes.
- **`SharedChangedBanner`'s "Share Again" button runs the same action as the toolbar's "Share List…"** (the system share sheet), rather than replaying whichever channel was last used — §10.10 doesn't specify which channel "Share Again" should use, and the last-used channel isn't tracked (`markShared` only stores a signature, not which action set it). The share sheet itself offers WhatsApp among its options.
- **The week's per-day meal-plan export data (`[ExportDay]`) is built directly in `ShoppingListContentView`**, not as a new `WeekPlanService` method — it has a single call site (the exporter), mirrors the same live/archived branch `listData` already uses, and §16's M10 file list doesn't call for a new service file.

## 2026-09-15 — M9: Shopping list & hand-added items

- **The share menu (§10.10's "⬆︎", §12) and `SharedChangedBanner` are not built.** M9's own Build list is explicit: `ShoppingListView`, `ShoppingItemRow`, `AddShoppingItemSheet`, the archived list display, the badge, Untick All — no `ShareService`, no share menu, no banner. Those, plus `lastSharedSignature`'s UI, are M10's read list (§10.10 "share menu, banner", §12). `WeekPlanService+Shopping.markShared` is still built now (it's in §8.2's given interface) but nothing calls it yet.
- **Weeks archived before M9 have no saved shopping list.** `ArchiveService.archiveEndedWeeks` only started building `ArchivedShoppingList` this milestone, so any week already archived by M6/M7/M8's version of `archiveEndedWeeks` has `archivedShoppingJSON == nil`. Per direction, `ShoppingListView` detects this (`archivedShoppingList(_:)` returning `nil` for an archived week, including one with no `WeekPlan` at all) and shows "No shopping list was saved for this week" instead of trying to rebuild one from today's live data, which would misrepresent what was actually bought at the time.
- **The Shopping tab's badge (§9.1) is computed by a separate invisible `ShoppingBadgeReporter` view in `RootTabView`, and written to a new `AppState.shoppingBadgeCount` rather than read back from `ShoppingListView` via a SwiftUI preference.** Verified in the Simulator that a `.preference` set inside a `Tab`'s own content in this iOS 18 `TabView`/`Tab` API never reaches an `.onPreferenceChange` on the enclosing `TabView` — each tab's content appears to be hosted in its own hierarchy for preference-propagation purposes, even though it renders fine and receives environment values normally. Routing the count through the already-`@Observable` `AppState` (§9.2) instead works correctly and needs no new mechanism.
- **`ShoppingListView`'s progress bar and "N of M ticked" text are split across two places** rather than combined in one header area as §10.10's wireframe draws them: the count text reuses `WeekNavigator`'s existing `subtitle` slot (empty when the list has no items), and the bar itself is the List's first row. This reuses the same shared navigator component the Plan screen already uses instead of a bespoke subtitle-less variant, and avoids showing the count twice.
- **`AddShoppingItemSheet` takes the already-picked `Ingredient` (and any existing `ManualShoppingItem`) rather than running `IngredientPickerSheet` internally.** `ShoppingListView` presents the picker itself first (plain `onSelect`, no `recipeCompletion`) and then presents `AddShoppingItemSheet` via `.sheet(item:)` once an ingredient is chosen — two sibling sheets in sequence, rather than nesting the amount form inside the picker's own `NavigationStack` the way `RecipeIngredientForm` does. `IngredientPickerSheet.recipeCompletion` is typed specifically around `RecipeLineDraft`/`RecipeIngredientForm`, and reusing it here would mean generalising that mechanism for a single call site; the two-sheet handoff is simpler and needs no changes to `IngredientPickerSheet` at all. The row's "Edit Added Item…" action skips the picker and opens `AddShoppingItemSheet` directly, pre-filled.
- **`WeekPlanService.statuses(for:sections:)` returns a status for every item, defaulting to `.unchecked` when no `ShoppingItemState` row exists yet**, rather than only returning entries for items that have been ticked at least once. §7.5 describes `ShoppingCheckEvaluator.status` per item but the service-level "for a whole list" function isn't fully specified; returning a complete map keyed by every current item is what both `ShoppingListView` (needs a status to render every row) and the Shopping badge (needs to count every unticked/needs-more item, including ones never touched) actually need.
- **`Dictionary(uniqueKeysWithValues:)` replaced with `Dictionary(_:uniquingKeysWith: { first, _ in first })`** in `WeekPlanService+Randomize.swift` and `WeekPlanView.swift`, per direction — both call sites already build their key arrays from sources that can't actually collide (meal IDs from a single fetch; slot IDs from `occurrences`), so this is a defensive swap with no behaviour change, not a fix for an observed crash.

## 2026-09-15 — M8 fixes: scroll to today, leftovers on skipped slots, tidy-ups

- **The Plan screen no longer scrolls to today's section on open — it always opens at Monday.** The M8 regression report was right that `DaySection`'s header `.id()` sat on the `Text` nested inside the new dice-button `HStack` rather than the header as a whole, so `ScrollViewReader.scrollTo` found nothing and did nothing; moving the `.id()` to the whole header fixed that specific bug. But further testing in the Simulator (with the id correctly on the header either way, and even reverting the header back to the exact pre-M8 `Text`-only version) showed `List` + `ScrollViewReader.scrollTo(anchor: .top)` lands one whole section past *any* requested day-header target in this Xcode/Simulator toolchain — not something introduced by M8. Swapping to the newer `scrollPosition(id:anchor:)` didn't help either: it never actually moved the list, whether set from `.onAppear` or as the `@State`'s initial value. Per direction, this is no longer worth chasing — the scroll-to-today mechanism (`WeekPlanContentView`'s `ScrollViewReader`/`.onAppear`, and `DaySection.headerID`) is removed; the list just opens at its natural top (Monday).
- **`WeekPlanService+Randomize.randomize`'s `.replaceAll` no longer deletes a cooked target's dependent leftovers when that target's meal type has no candidates left after excluding last week's meals.** Previously it deleted dependents for every cooked target up front, before checking whether `MealRandomizer` could actually find a replacement — so a skipped slot (§7.6: added to `skippedNoCandidates`, left untouched) still lost its leftovers for nothing. Dependents are now only deleted for targets whose meal type has a non-empty pool once `excludedMealIDs` is removed, computed the same way `MealRandomizer` itself decides whether a slot is skippable.

## 2026-09-15 — M8: Randomiser

- **Row Shuffle and the picker's Shuffle button don't call `WeekPlanService+Randomize.randomize`.** §8.2's bulk algorithm (used by the toolbar 🎲 menu and the day-header 🎲) always deletes a replaced cooked slot's dependents outright — there's no dialog, just the confirmation's extra sentence. But §10.1's row table and §14 ("Removing, changing or shuffling a cooked meal with leftovers → Dialog: remove leftovers too / keep as cooked") both say a single-slot Shuffle needs the same dependent-leftovers dialog as any other reassignment. So single-slot Shuffle (`WeekPlanService.randomMeal(for:)`, new, not in §8.2's given interface) just picks one random meal via `MealRandomizer` and then runs it through the *existing* `dependentDecision`/`assign(dependents:)` flow already built for M6/M7 — same dialog, same choice — rather than the bulk method's unconditional removal.
- **Confirmation-dialog copy for "Randomise Whole Week" and "Randomise `<Day>`" isn't given verbatim** — §10.1 only spells out the Breakfasts/Lunches/Dinners example ("Fill Empty Dinners", "Replace All Dinners"). Extended the same pattern: whole week uses "Fill Empty Meals" / "Replace All Meals" (matching the existing Copy dialog's "Fill Empty Meals" text); a day uses "Fill Empty `<Day>`" / "Replace All `<Day>`" (e.g. "Fill Empty Monday").
- **Row Shuffle and the picker's Shuffle button reuse `MealRandomizer.skippedCandidatesMessage`** (new, alongside `MealRandomizer`, mirroring `LeftoverRules`'s own copy-builder precedent) for the "not enough candidates" case on a single slot — same copy as the bulk alert, naming just that one meal type. Not spelled out for the single-slot case, but §14's "Randomise when every candidate was used last week → The slot stays empty, with an explanation alert" applies equally here.
- **`MealSlotRow`'s leading-swipe Shuffle is offered on every row, filled or empty** — §10.1 marks trailing-swipe Remove "(filled)" explicitly but leaves leading-swipe Shuffle unqualified, and an empty "Add lunch" row can just as usefully be filled by a shuffle. The context-menu Shuffle stays inside the existing "(filled)" block, since the context menu itself only appears for filled rows.
- **`WeekPlanService+Randomize.randomize` applies `MealRandomizer`'s assignments directly to each slot's `meal`/`leftoverOfSlotID` rather than calling `assign`** (§8.2 step 5 says "apply with `assign`"). Dependents have already been resolved earlier in the same method (the dependent-deletion and locking steps), and the whole batch saves once at the end, so routing each assignment back through `assign` — which re-checks dependents and calls `context.save()` itself — would redo work already done and save once per slot instead of once per call.

## 2026-09-15 — M7.1: "Good as Leftovers"

- **`Meal.goodAsLeftovers` added directly to `SchemaV1`, no migration stage**, per M7.1's instruction — the app hasn't been released. The Simulator's existing store (built against the pre-M7.1 schema) failed to open with the new field until the app was deleted from the Simulator and reinstalled; no code change needed, just noted here per the milestone's own instruction to record it.
- **`WeekPlanService.fetchMeal(id:)` changed from `private` to internal**, same precedent as `slot(at:in:)` (M7's decision note): `WeekPlanService+Leftovers.swift` needs it to look up a candidate meal's `goodAsLeftovers` flag before calling `LeftoverRules`, and it was already exactly the lookup `copyWeek` uses.
- **The context-menu gate ("Mark as Leftovers", "Leftovers for Tomorrow's …") lives in `DaySection.menuFlags`, not in `LeftoverRules.slotMenuFlags`.** §7.7's v1.3 note is explicit that `LeftoverRules` "stays a pure function of occurrences and doesn't know about the flag" — only `WeekPlanService.leftoverSourceCandidates` applies it. `slotMenuFlags` is itself an addition beyond §7.7's given interface (M6's decision note), precomputed per-row from `PlanWeekContext` with no further service calls, so `DaySection` checks `slot.meal?.goodAsLeftovers` itself and short-circuits to `.none` before calling into `LeftoverRules` — keeping the domain function pure while still gating both menu items (per §10.1, both require the flag).

## 2026-09-15 — M7: Leftovers

- **`WeekPlanService.assign` gained a `dependents: DependentLeftoversAction = .keepAsCooked` parameter**, not in §8.2's skeleton. The spec says replacing a cooked slot's meal while leftovers depend on it must resolve those dependents the same way `clearSlot` does (§8.2: "the UI asks first"), but `assign`'s given signature has no way to carry that choice through — only `clearSlot` takes a `dependents:` parameter. Added it with a harmless default so every existing M6 call site is unaffected; `assign` only consults it when it's actually replacing a **cooked** slot's meal with a **different** meal (mirroring `clearSlot`'s own dependents check), so assigning the same meal or assigning over a leftovers slot never touches it.
- **Added `WeekPlanService+Leftovers.assignmentDecision(forAssigning:at:)` and `dependentDecision(forCookedAssignmentOf:at:)`**, beyond §8.2's listed interface. `MealPickerSheet`, `AddToPlanSheet` and the "New Meal → assign" flow all need the identical two-step decision (leftovers prompt, then dependent-leftovers prompt) described in §10.2/§10.3/§10.8 before calling `assign`. Putting that decision in the service — rather than duplicating the candidate/dependent lookups in three views — keeps it unit-tested in `WeekPlanServiceTests` and the views only need to react to the result.
- **Added `WeekMath.fullDayName(_:)`** (fixed English, mirroring the existing `shortDayName`) and `LeftoverRules.dependentPromptTitle(for:)`/`dependentPromptMessage(for:)` (pure text builders, not in §7.7's listed interface) so the dependent-leftovers dialog's exact copy ("Monday dinner has leftovers planned" / "Tuesday lunch is leftovers from this meal.") is built once, tested in `LeftoverRulesTests`, and shared between the Plan screen's Remove flow and the two assignment sheets.
- **§10.3 B's example message only covers one dependent slot.** When more than one slot depends on the same cooked meal, the message joins them: "Tuesday lunch and Wednesday lunch are leftovers from this meal." (Oxford-less "and", pluralised "are") — the simplest reading that extends the given singular example.
- **`Shared/DependentLeftoversDialog.swift` holds both of §10.3's prompts, not just the dependent one.** The spec's file-list comment names it for prompt B only, but §10.3 itself is titled "Leftovers prompts (**shared**)" and groups A and B together; `MealPickerSheet` and `AddToPlanSheet` both need prompt A too, so it lives in the same file as a second small view-modifier rather than a separate one.
- **`ArchiveService`'s private `sourceLabel(for:)` now delegates to the new `WeekPlanService.sourceLabel(for:)`** instead of duplicating the same by-ID slot lookup — the two were previously identical, and `WeekPlanService` is easy to construct from `ArchiveService`'s own `context`/`now`/`calendar`.
- **`copyWeek` needed no changes.** M7's read list mentions "update copyWeek remapping," but the leftover-remapping logic (map old slot IDs to new ones; fall back to cooked when the source slot wasn't copied) was already built and tested in M6, per that milestone's decision note, and matches §8.2's description exactly as-is.

## 2026-09-15 — M6 fixes: plan layout, copy flow and read-only rows

- **`MealSlotRow`'s meal-type column uses a manual `HStack(Image, Text)` instead of `Label`.** Verified in the Simulator that `Label(title, systemImage:)` inside a width-constrained `.frame()` can silently drop its title and render icon-only, rather than wrapping or truncating — worse than the original "Break-fast" wrapping bug it was meant to fix. A plain `HStack` doesn't have that failure mode. The column width is `@ScaledMetric` off a baseline (132pt) generous enough for "Breakfast" plus its icon at the default Dynamic Type size, combined with `.fixedSize(horizontal: true, vertical: false)` on the `Text` so it's never compressed below that.
- **`ScrollViewReader` now scrolls to the day header's own id, not the whole `Section`.** Scrolling to today's `DaySection` left the "· TODAY" header hidden behind the `WeekNavigator` safe-area inset — apparently `scrollTo(anchor: .top)` on a `List` `Section` doesn't reliably account for a floating `safeAreaInset` overlay. Tagging the header `Text` itself with `DaySection.headerID(dayIndex:)` and scrolling to that fixed it, verified in the Simulator.
- **"Copy Last Week" and "Copy to This Week" now share one `startCopy(source:target:)` path** (empty-source alert, immediate fill-empty when the target is empty, otherwise the Fill Empty/Replace confirmation) instead of two divergent implementations — §10.1 describes the same behaviour for both, just with source and target swapped.

## 2026-09-15 — M6: Weekly plan & archiving

- **§10.3 (leftover prompts, including the dependent-leftovers dialog) is entirely deferred to M7.** It isn't in M6's read list, and can't actually be exercised yet: nothing in M6 can create a leftover-linked `MealSlot` (that's `WeekPlanService+Leftovers`, M7). `WeekPlanService.clearSlot(at:dependents:)` and `dependentLeftovers(of:)` are still fully implemented now (they're core `§8.2` "reading, slots, copy" — plain queries by `leftoverOfSlotID`, no `LeftoverRules` algorithm needed) so `copyWeek`'s leftover-remapping and `MealStore.delete`'s dependent-cleanup are correct and unit-tested. The M6 UI (`MealSlotRow` swipe/context-menu "Remove", `MealPickerSheet`'s "Remove from Plan") just calls `clearSlot(dependents: .remove)` directly with no confirmation dialog — safe since the dependents set is always empty today. M7 adds `DependentLeftoversDialog` and wires the choice in.
- **`RandomizeMenu.swift` and the 🎲 controls aren't built.** M6's read list says "no randomise" for §10.1; the toolbar and section headers simply omit them until M8.
- **`PlanPosition`/`PlanOccurrence` (formally §7.7, `LeftoverRules.swift`) and `RandomizeMode` (formally §7.6, `MealRandomizer.swift`) added early, same precedent as M2's early `MealDraft`.** `WeekPlanService`'s core M6 methods (`assign`, `clearSlot`, `occurrences`, `copyWeek`) need these types now; `LeftoverRules.label(for:)` is included too since `ArchiveService` needs it to build a leftover slot's `leftoverSourceLabel`. The actual algorithms (`LeftoverRules.sourceCandidates`, `MealRandomizer.randomize`) land with M7/M8 in the same files.
- **`Domain/ArchiveSnapshots.swift` omits `ArchivedShoppingList`, and `ArchiveService.archiveEndedWeeks` skips step 3 (the shopping-list snapshot).** M6's read list is explicit: "§8.1 (slots only; the shopping snapshot comes in M9)" — `ArchivedShoppingList` needs `ShoppingListSection`/`CheckStatus` from `ShoppingListBuilder`/`ShoppingCheckEvaluator`, which don't exist until M9. `ArchivedSlot` snapshots (and `archivedSlot(_:)`) are fully implemented and tested now.
- **`AppRoute`'s `Hashable`/`Equatable` conformance is hand-written, not derived.** Discovered a reproducible issue with this Xcode 26 toolchain (Swift 6, `-enable-upcoming-feature MemberImportVisibility`): a `NavigationLink(value: AppRoute.someCase(...))` call would fail to compile with "type 'AppRoute' does not conform to protocol 'Equatable'" depending on incidental details of which files in the same incremental-build batch happened to `import SwiftData` — flaky across clean rebuilds, not fixed by adding the import everywhere. Writing `==`/`hash(into:)` by hand (comparing each case's payload by its `id`, not the model's own identity) sidesteps whatever is going on with derived-conformance visibility for `@Model` classes across files, and is stable across repeated clean builds.
- **`MealPickerSheet` and `AddToPlanSheet` always assign as cooked; no leftovers prompt (§10.3 A).** Same reasoning as above — `leftoverSourceCandidates` is M7. Tapping a meal, or "Add" in `AddToPlanSheet`, calls `WeekPlanService.assign` directly.
- **`MealEditorView` gained `presetMealType` and `onSave` parameters** (both optional, default `nil`, so every existing call site is unaffected) so `MealPickerSheet`'s "+ New Meal" (§10.2) can preselect the slot's meal type and assign the saved meal to the plan without a second round trip through the picker.

## 2026-09-15 — M5 fixes: photo processing performance

- **`ImageProcessor.prepare` gained a `UIImage` overload.** The camera path (`CameraPicker`) now hands its captured `UIImage` straight to `ImageProcessor` instead of encoding it to JPEG on the main actor first (`jpegData(compressionQuality: 1)` on a 12–48 MP image was blocking the UI right after "Use Photo"). `MealEditorPhotoSection` sets `isProcessing = true` synchronously before handing off to either overload, so the progress overlay appears immediately rather than after the first `await`.
- **The `Data` overload now downsamples via ImageIO** (`CGImageSourceCreateThumbnailAtIndex` with `kCGImageSourceThumbnailMaxPixelSize = 1600` and `kCGImageSourceCreateThumbnailWithTransform = true`) instead of decoding the full image with `UIImage(data:)`, which held the entire bitmap in memory (≈190 MB for a 48 MP photo) just to immediately downscale it. The 300×300 thumbnail is then cropped from that already-downsampled image, not the original, for both overloads.
- **`UIGraphicsImageRendererFormat.opaque = true`** on both the resize and crop renderers — without it, a transparent PNG's alpha is composited onto black before JPEG encoding (JPEG has no alpha channel), turning transparent areas solid black. `opaque = true` fills with an opaque backing first.
- **§14's "No camera (Simulator)" edge case is confirmed outdated, not a bug to fix.** `UIImagePickerController.isSourceTypeAvailable(.camera)` returns `true` on the Xcode 26 / iOS 26 Simulator (it now exposes a virtual camera), so "Take Photo" correctly shows there. The code still hides the option whenever that API reports no camera; the platform's answer has just changed since the spec's table was written. No code change needed — noted here so a future milestone doesn't "fix" this as a regression.

This is the platform API's real answer, not a bug in `MealEditorPhotoSection` — the code correctly hides the option whenever that API says no camera is available, on whichever OS/Simulator combination that's true.

## 2026-09-14 — M4 fixes: recipe line editing and polish

- **`RecipeIngredientForm` took a `Mode` enum instead of three optional closures.** The original `onAdd`/`onAddAndNext`/`onSave` optional-closure design let `MealEditorView`'s edit-mode call site pass its update closure as an unlabelled trailing closure; in Swift 6 that bound to `onAdd` (the first optional closure parameter) rather than `onSave`, so "Done" silently discarded edits. Replaced with `enum Mode { case add(onAdd:, onAddAndNext:); case edit(existing:, onSave:) }` — a single required, non-defaulted parameter that makes the same mistake a compile error (there's no closure left for a trailing closure to ambiguously match).
- **`RecipeIngredientForm` edit mode gained a Cancel button.** It only had "Done" before; §10.6 item 4 says "In edit mode: Done only" for the toolbar's confirmation side but doesn't say Cancel is absent, and a sheet with unsaved edits and no way to back out is a trap. Added a `.cancellationAction` "Cancel" alongside "Done".
- **`MealDetailView.duplicate()` now pushes the new meal.** §10.5 doesn't say explicitly, but showing the *old* meal after "Duplicate" (as M4 originally did) is confusing — you asked to duplicate, you should land on the copy. Threading a `Binding<NavigationPath>?` down from the Meals tab's `NavigationStack` (via `appRouteDestinations(path:)`) lets `duplicate()` pop itself and push the copy, so Back still returns to the library rather than the original meal. The binding is optional and only the Meals tab supplies one for now — reaching `MealDetailView` via Settings → Library → Ingredients → a meal still duplicates correctly, it just won't auto-navigate to the copy from that path.
- **Unquantified lines ("to taste") now show no amount text**, superseding the M4 decision below — verified in the Simulator that "To taste" read as odd placeholder copy next to real amounts; omitting the trailing text entirely (as the mockups do for every other row) is cleaner and needs no invented copy.
- **Added `Domain/DurationFormatter.swift`, not listed in §5.2's file list.** `MealEditorView`'s Time picker showed raw minutes ("90 min") for values that read far more naturally as hours ("1 hr 30 min"). This is pure `Foundation`-only formatting logic with its own unit tests (`DurationFormatterTests`), so it belongs in `Domain/` alongside `QuantityFormatter` even though §5.2 doesn't name it — the folder rule enumerates what M1–M12 each need, not a closed list.

## 2026-09-14 — M3 fixes: navigation destinations and polish

- **All navigation is value-based, through `Shared/AppRoute.swift`.** Mixing a view-based `NavigationLink { Destination() }` (in `SettingsView`) with a value-based `.navigationDestination(for: Ingredient.self)` declared lower down (in `IngredientLibraryView`) caused SwiftUI to warn "A navigationDestination for MealPlanner.Ingredient was declared earlier on the stack" and silently do nothing on tap. Fixed by routing every push through a single `AppRoute` enum, with `.navigationDestination(for: AppRoute.self)` declared exactly once per tab, at the root, via the `.appRouteDestinations()` modifier. **No screen may declare its own `navigationDestination(for:)` — add new cases to `AppRoute` instead** (M4 will add `.meal(Meal)`).

## 2026-09-14 — M2 fixes: test container lifetime and draft normalisation

- **Real cause of the M2 test crash: dangling `ModelContext`, not parallelism.** `IngredientStoreTests.makeStore()` and `MealStoreTests.makeContext()` created a local `ModelContainer`, handed out a store/context built on it, and let the container fall out of scope — a `ModelContext` doesn't retain its container, so once the container deallocated, the next fetch trapped inside SwiftData (`EXC_BREAKPOINT`/`SIGTRAP`). It looked parallelism-related because Swift Testing's concurrent scheduling changed which test's container got collected first, but the bug was present regardless. Fixed by storing the container as a `let` property built in each suite's `init() throws`, so it lives for the whole test's lifetime. No workaround (e.g. `-parallel-testing-enabled NO`, `.serialized`) needed or used.

## 2026-09-14 — M2: App shell, stores & sample data

- **Built `MealDraft` (and `RecipeLineDraft`/`StepDraft`) two milestones early.** §8.3 specifies `MealStore.create(from draft: MealDraft)` and `update(_:from:)` exactly, but `MealDraft` itself is formally introduced in M4 (§10.6) alongside the editor UI. Since M2 explicitly asks for a full `create`/`update`, and changing a service's signature later is worse than adding a small pure value type now, I added `Features/Meals/MealDraft.swift` early — data only, no UI, no view files. M4 will build `MealEditorView`/`RecipeIngredientForm` against this same struct without touching `MealStore`.
- **`IngredientStore`/`MealStore` don't yet call `ArchiveService.archiveEndedWeeks()` first.** §5.1 says every mutating service method must archive-first, but `ArchiveService` doesn't exist until M6, which explicitly says "Add archive-first calls to every mutating method in all stores." Not a deviation — just sequencing implied by the milestone breakdown.
- **`IngredientStore.merge` manual-item quantity combination.** §8.4 says "add A's quantity when the base units match" but the model stores a single raw `quantity` + `unit`, not a base-unit amount. I convert both to base units, sum, then convert back to the target item's unit (e.g. 500 g + 0.5 kg → 1 kg), since that's the simplest reading that produces one coherent merged amount in the target's existing unit.

## 2026-09-14 — M1: Models & domain foundations

- **`SchemaV1.versionIdentifier` is `static let`, not `static var`.** SPEC §6.5 writes `static var versionIdentifier = Schema.Version(1, 0, 0)`, but under Swift 6 with Default Actor Isolation = MainActor, a mutable (`var`) static stored property is flagged as "not concurrency-safe... nonisolated global shared mutable state" (the `VersionedSchema` protocol requirement is `nonisolated`). Since the value is never mutated, changing it to `let` is the simplest fix that satisfies both the protocol and Swift 6 strict concurrency, with no behaviour change.
- **`AppError` copy text for `.ingredientInUse` and `.invalidName`.** SPEC §13.3 gives exact copy only for `.weekIsArchived` ("This week has ended and can't be changed."), and §10.9/§10.6 give copy that maps naturally to `.duplicateIngredientName` and `.imageProcessingFailed`. No exact string is specified for `.ingredientInUse` or `.invalidName`, so I wrote minimal, reasonable placeholder copy ("Used in N meal(s)." / "Please enter a name."). These aren't exercised by any UI yet (that comes in M3/M9) — worth a final copy pass when those screens are built.
- **`QuantityParser` unicode fraction support limited to ½, ¼, ¾.** These are the only vulgar fractions in SPEC §7.2's test table and the only ones implied by the §10.7 hint text ("Enter a number like 2, 1.5 or 1/2"), so I didn't add other unicode fractions (⅓, ⅔, etc.) to avoid scope creep beyond what's specified.
